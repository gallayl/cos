# COS TypeScript SDK & Berry Compiler

## 1. Overview

Introduce TypeScript as an additional application development language for COS, while keeping the existing Berry VM as the execution runtime.

The goal is to provide a modern, developer-friendly scripting environment with:
- TypeScript syntax and type checking.
- Intelligent code completion and IntelliSense.
- API documentation and parameter hints.
- Syntax validation and compile-time diagnostics.
- A custom TypeScript-to-Berry compiler.
- In-device browser-based code editing.
- Direct application deployment to the COS filesystem.

**Core architectural principle:**

TypeScript is the authoring language, Berry is the compilation target, and the existing Berry VM remains the runtime.

All TypeScript parsing, type checking and code generation happen in the browser, not on the ESP32. The device only stores the source files and generated Berry code, serves the frontend and executes Berry applications.

Existing Berry applications must remain fully functional.

### Main responsibilities

**Frontend:**
- Provide the complete development environment.
- Edit and manage application source files.
- Provide TypeScript intelligence and API documentation.
- Compile TypeScript into Berry.
- Display diagnostics and generated output.
- Upload source and compiled files to the device.

**COS firmware:**
- Serve the frontend application.
- Provide authenticated filesystem access.
- Store TypeScript and Berry files.
- Execute generated Berry applications through the existing runtime.
- Require no TypeScript compiler or JavaScript runtime.

## 3. Frontend technology

### Framework

Use the existing FuryStack Shades framework.

### Code editor

Use:

`@furystack/shades-monaco`

https://www.npmjs.com/package/@furystack/shades-monaco

Use Monaco's TypeScript language service for:
- Syntax highlighting.
- Intelligent autocomplete.
- Type information on hover.
- Parameter hints.
- Go to definition.
- Diagnostics.
- Code navigation.

Avoid registering all Monaco languages and features. Only include the functionality required for TypeScript development.

### TypeScript SDK integration

Register the COS declaration files as an additional TypeScript library using Monaco's `addExtraLib()` functionality.

The editor must understand COS-specific APIs without requiring the user to install additional dependencies.

### Compiler execution

Run the custom compiler inside a dedicated Web Worker.

Reasons:
- Avoid blocking the editor UI.
- Keep compilation isolated from the rendering process.
- Avoid consuming ESP32 resources.
- Allow compilation to be triggered independently of editor changes.

The initial implementation should compile explicitly through a Compile action, rather than compiling the entire application on every keystroke.

## 4. COS TypeScript SDK

Create a dedicated SDK package containing TypeScript declaration files.

Suggested structure:

```text
packages/
  cos-sdk/
    src/
      index.d.ts
      ui.d.ts
      console.d.ts
      network.d.ts
      filesystem.d.ts
    package.json
```

The SDK represents the APIs actually available in the existing Berry runtime.

Example:

```typescript
declare namespace ui {
  function fill_screen(color: number): void;

  function fill_rect(
    x: number,
    y: number,
    width: number,
    height: number,
    color: number
  ): void;

  function draw_text(
    x: number,
    y: number,
    text: string,
    color: number,
    background: number
  ): void;

  function timer(
    interval: number,
    callback: () => void
  ): void;

  function touch(): [number, number] | null;
}

declare function log(message: string): void;

declare function action(command: string): number;
```

The declarations above are illustrative. The actual SDK must reflect the existing COS Berry APIs.

### SDK requirements

- Use existing Berry API names wherever practical.
- Provide accurate parameter and return types.
- Include documentation comments for all public APIs.
- Provide completion and hover documentation in Monaco.
- Avoid exposing APIs that cannot execute on the device.
- Keep SDK definitions independent from the compiler implementation.

### Single source of truth

Long term, consider introducing a shared API definition schema from which the following can be generated:

1. TypeScript declaration files.
2. Editor API documentation.
3. API reference documentation.
4. Potentially native binding registration code.

This avoids manually maintaining multiple representations of the same API.

## 5. TypeScript-to-Berry compiler

Create a dedicated compiler package.

Suggested structure:

```text
packages/
  cos-typescript/
    src/
      parser/
      validator/
      lowering/
      ir/
      berry/
        code-generator.ts
        expression-generator.ts
        statement-generator.ts
        class-generator.ts
      diagnostics/
      source-maps/
```

### Compiler pipeline

```text
TypeScript source
       |
       v
TypeScript parser
       |
       v
AST generation
       |
       v
Type checking and diagnostics
       |
       v
COS language validation
       |
       v
AST lowering / optional COS IR
       |
       v
Berry code generation
       |
       v
Generated .be source
```

### Implementation approach

Use the TypeScript Compiler API.

Relevant capabilities:
- `createSourceFile()`
- `Program`
- `TypeChecker`
- AST node visitors.
- Compiler diagnostics.
- AST factory APIs.

Do not use string replacement or regular-expression-based transformations as the primary compilation mechanism.

Do not use the standard TypeScript printer to generate the final Berry output.

Implement a dedicated Berry code generator that translates supported AST nodes into valid Berry syntax.

An intermediate representation is recommended to separate TypeScript-specific parsing and validation from Berry-specific code generation.

For an initial implementation, direct AST visitor-to-Berry-emitter generation is also acceptable.

### Compiler requirements

- Deterministic output.
- Readable and consistently formatted Berry source.
- Meaningful compiler diagnostics.
- Original TypeScript source location tracking.
- Explicit rejection of unsupported syntax.
- No silent semantic degradation.
- Automated tests for generated output.
- No dependency on firmware-specific functionality during compilation.

## 6. Initial supported TypeScript subset

The project does not aim to support the entire TypeScript or JavaScript language.

It provides a restricted, explicitly defined TypeScript authoring language compatible with the Berry runtime.

| Feature | Initial support |
|---|---|
| `const` and `let` | Yes |
| Primitive types | Yes |
| Type aliases | Yes, compile-time only |
| Interfaces | Yes, compile-time only |
| Functions | Yes |
| Arrow functions | Yes |
| Classes | Yes |
| Class properties | Yes |
| Class methods | Yes |
| Constructor | Yes |
| Single inheritance | Later |
| Arrays | Yes |
| Simple objects | Yes, with explicit mapping rules |
| `if` / `else` | Yes |
| `switch` | Yes |
| `while` | Yes |
| Basic `for` loops | Yes |
| `for...of` | Yes |
| Template strings | Yes, through lowering |
| Imports / exports | Restricted |
| Enums | Later |
| Destructuring | Later |
| Spread / rest | Not initially |
| Promises | Not initially |
| Async / await | Not initially |
| Generators | Not initially |
| Decorators | Not initially |
| Arbitrary npm dependencies | Not supported |

### Important semantic rules

The compiler must explicitly define the following mappings:

- `const` and `let`: compile to Berry variables. Compile-time immutability is enforced by TypeScript.
- `this`: translate to Berry `self`.
- `null` and `undefined`: define a consistent mapping to Berry `nil`.
- `===` and `!==`: define supported equality semantics instead of blindly replacing operators.
- Truthiness: enforce boolean conditions where appropriate.
- Array `.length`: translate to the corresponding Berry array operation.
- Template strings: lower into supported string operations.
- Class property initialization: generate appropriate Berry initialization code.
- Access modifiers: compile-time only unless an explicit runtime equivalent is implemented.

Unsupported constructs must produce compiler diagnostics pointing to their original TypeScript source locations.

The compiler must never silently generate code with potentially different runtime behavior.

## 7. COS application format

Preserve the existing COS application execution contract.

Currently, an application returns a class that COS instantiates and initializes through:

```berry
setup(content, width, height)
```

An optional `teardown()` method can be used for cleanup.

The corresponding TypeScript format:

```typescript
export default class MyApp {
  setup(
    content: unknown,
    width: number,
    height: number
  ): void {
    // Application initialization
  }

  teardown(): void {
    // Cleanup
  }
}
```

### Compiler mapping

- `export default class` represents the COS application entry point.
- TypeScript type annotations are removed.
- The generated Berry source defines the application class.
- The generated source ends with `return MyApp`.
- COS instantiates the returned class.
- Existing `setup()` and `teardown()` conventions remain unchanged.

No JavaScript module loader is required for the initial implementation.
