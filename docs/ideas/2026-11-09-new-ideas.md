### R22 — Frontend incremental dependency-aware compilation

- **Priority:** P1 | **Complexity:** M | **ROI:** High | **Risk:** Low
- **Source:** `frontend/tools/compile-storage.ts`, `frontend/src/ide/import-specifiers.ts`, `frontend/src/ide/import-resolution.ts`, `frontend/src/editor/editor-app.tsx`
- **Problem:** `compile-storage` compiles all `storage/ts/*.ts` independently with no dependency awareness; the IDE compiles single files via `astToBerry(getAst(...))` directly. Relative imports resolve at runtime to `.be` files, so compiling a file with unbuilt/stale dependencies leads to runtime import failures. Timestamp-based incremental compilation with transitive dependency resolution is needed for better DX.
- **Spec / acceptance criteria:**
  - When compiling a `.ts` file that has relative imports, transitively discover dependencies via `collectRelativeImportSpecifiers()` and resolve to `.ts` paths.
  - For each dependency, compare mtime of source `.ts` vs compiled `.be` in the target output dir; compile if missing or out of date.
  - Support both `frontend/tools/compile-storage.ts` (build tool) and IDE compilation flows.
  - Skip non-TS deps (`@cos/*`, `@berry/*`) and type-only imports (already stripped). Handle cycles gracefully with clear errors.
  - Preserve existing behavior for files with no relative imports.
- **Implementation notes:**
  - Leverage existing import extraction/resolution utilities. Build a dependency graph with cycle detection.
  - For `compile-storage`, make compilation dependency-aware (or add a mode) while keeping `verifyStorage()` semantics intact.
  - For IDE, ensure dependencies are built before upload/run when compiling a file with imports.
- **Progress:**
  - [x] Dependency graph building from relative imports (IDE compile flow, transitive relative TS imports)
  - [x] Timestamp-based up-to-date checking (IDE: compare dependency `.ts` vs `.be` `mtime` from device listings; treat missing `.be` as outdated)
  - [~] Integration into compile-storage and IDE flows (IDE compile: dialog listing outdated/missing deps + optional auto-compile/write of deps in module mode; compile-storage/build-tool flow still pending)
  - [ ] Tests added
  - [ ] Documentation updated

### R23 — Simple callback-based HTTP server API for Berry/TS (Express-like)

- **Priority:** P2 | **Complexity:** L | **ROI:** Medium-High | **Risk:** Medium-High
- **Source:** `components/http_server/*`, `components/berry_lang/src/berry_network.cpp`, `frontend/src/cos-sdk/network.d.ts`
- **Problem:** No script-facing HTTP server API with routing/callbacks exists. For simple chat/multiplayer games and local device services, developers need an Express-like server API usable from Berry/TS scripts.
- **Spec / acceptance criteria:**
  - Add Berry bindings (e.g. `@cos/http` or `http/server`) exposing `createServer()`, route registration (`app.get/post/put/delete/...`, or `app.route()`), middleware support (basic), and `listen(port, [host])`.
  - Request object provides method, path, headers, query, body (with size limits). Response object supports `status()`, `set()`, `send()`, `json()`, `end()`.
  - TypeScript SDK declarations added with full type awareness.
  - Built on existing `http_server` component or ESP-IDF HTTP server; callback bridging between C and Berry with proper lifetime management.
  - Respects ESP32 memory/stack constraints; documented limitations (payload sizes, concurrent connections).
  - Examples for simple chat/multiplayer use cases.
- **Implementation notes:**
  - Route matching (path params/query parsing) - keep simple initially.
  - Body parsing for common content types (text/json).
  - Need to handle Berry callback invocation from HTTP server task context safely.
  - Consider security/auth if exposed on network; document LAN-only usage patterns.
- **Progress:**
  - [ ] API design and TypeScript SDK types
  - [ ] Native/C Berry bindings
  - [ ] Routing and request/response handling
  - [ ] Tests and examples
  - [ ] Hardware validation

### R24 — Berry bytecode (`.bec`) persistence with opt-in configuration

- **Priority:** P2 | **Complexity:** M | **ROI:** Medium-High | **Risk:** Medium
- **Source:** `build/berry-source/src/be_bytecode.{h,c}`, `components/berry_lang/src/berry_runtime.cpp`, `components/shell/src/shell_script.c`
- **Problem:** Berry scripts are compiled from source on every load (`be_loadbuffer`), increasing memory pressure and startup time. Berry VM supports bytecode save/load via `be_bytecode_save/load` and `compile()` can load `.bec` files.
- **Spec / acceptance criteria:**
  - Add opt-in configuration (build-time sdkconfig/define or runtime config on flash) to enable bytecode persistence.
  - When enabled, save compiled bytecode to `.bec` files alongside source files (`.be`/module paths) when loading/compiling from source.
  - On load, check for valid `.bec` file; use it if present and up to date relative to source mtime (or other freshness check). Fall back to source compilation if missing/stale/corrupt.
  - Integrate into all load paths: `berry_runtime_exec_file`, `berry_runtime_run_file`, `berry_runtime_open_app`, and `native_cos_import` for relative modules.
  - Handle corruption gracefully (Berry raises `bytecode_error` for corrupt `.bec` - must be caught and fall back to source).
  - Document memory/time benefits and limitations.
- **Implementation notes:**
  - Need to extract/save proto/closure appropriately using Berry APIs. The test shows `fout.savecode(fn)` after `compile()` in Berry; C-level integration needs care.
  - Track freshness (source mtime vs `.bec` mtime). Invalidate on source change.
  - Store `.bec` in same VFS locations as source files (flash/sdcard). Consider flash wear.
  - Version/format compatibility - pin to bundled Berry version.
- **Progress:**
  - [ ] Configuration mechanism design
  - [ ] Bytecode save/load integration
  - [ ] Freshness checking and fallback logic
  - [ ] Integration across all load paths
  - [ ] Tests (including corrupt bytecode handling)
  - [ ] Hardware validation and measurements
